# ADR-0004 · 渐进添加哲学：前一步完美才加下一步

- **状态**：已采纳
- **日期**：2026-05-18
- **背景**：用户明确表示"前一步完成完美了再加下一步"。这条原则对项目质量影响巨大，必须正式记录并在文档中贯彻执行。

---

## 决策

**任何机制的添加，必须满足前置阶段的"完美标准"才能开始**。

### 三档"完美标准"

每个 baseline 阶段和 module 卡片都必须明确给出三档：

| 档 | 含义 | 通过这档才允许 |
|---|---|---|
| **MVP（最小可运行）** | 能跑起来，没崩溃 | 写测试、查 bug |
| **完整（feature complete）** | 所有功能都实现 | 进入下一阶段开发 |
| **完美（polished）** | 调参收敛、视觉合格、性能达标 | 答辩 / 模块叠加 |

> "完美"≠ 永不重构。完美意味着**当前阶段不再是项目瓶颈**。

### 为什么这样

#### 反例：跨阶段欠债

如果 M3 NEAT 拓扑进化"差不多能跑"就跳到 M4 多线程，M4 可能因为 NEAT 偶尔产生坏拓扑导致死锁。这时你不知道是 M3 的问题还是 M4 的问题——**两个阶段的 bug 互相污染**。

#### 正例：阶段隔离

M3 必须做到：跑 200 代连续无崩溃 + 物种数稳定 + 适应度上升明显。**确认 M3 没问题再做 M4**——出问题就是 M4 的，不会怀疑 M3。

---

## 检查清单（每阶段结束必走）

```
□ MVP 检查
  □ 编译通过，CI 绿
  □ headless 训练 30 代不崩溃
  □ 单元测试覆盖核心数据结构

□ 完整检查
  □ 所有计划接口都有实现（不是 TODO）
  □ 所有计划事件都有发布
  □ 所有可视化元素都接入

□ 完美检查
  □ 关键指标达成（如适应度提升 > X、物种数 > Y）
  □ 视觉验收（截图归档）
  □ 性能验收（每秒 tick 数 ≥ 目标）
  □ 文档更新（决策、调参经验记录）
  □ ADR / 经验日志补完
```

每个 baseline 文档（M0-M5）和 module 卡片都给出具体的**关键指标值**。

---

## 当现实和理想不符怎么办

不是所有机制都能"跑出预期效果"（参见 ADR-0002 的档次承诺）。

### 中确定性 / 低确定性机制的特殊规则

如果一个 🟡 或 🔴 档机制经过 **3 次合理调参** 后仍未跑出预期：

1. 启用 **降级版**（每个模块卡片都给出降级方案）
2. 写入 `docs/experience_log.md` 记录失败现象与排查过程（这本身是答辩素材）
3. **不阻塞下一阶段**——降级版本验收通过即可前进

> 例：F-COMM 信号语义没涌现 → 降级为"信号场动态可视化"，至少视觉上有看头，答辩时讲"通信涌现的难度"。

---

## 例外情况

某些跨阶段优化（如发现 M0 接口需要修补支持 M5 地形）允许"回头改"，但必须：

- 写入 `docs/adr/` 形成新决策
- 评估对已完成阶段的影响
- 对已通过的"完美检查"重新执行

```

M1  连续 2D MVP       ✅✅⛳   (完整通过)
M2  可视化接入        ✅✅✅   (完美通过)
M3  NEAT 升级         ⬜⬜⬜
```

- ⬜ 未开始
- ✅⛳⛳ MVP 通过
- ✅✅⛳ 完整通过
- ✅✅✅ 完美通过

只有 ✅✅✅ 才能开始下一阶段。
