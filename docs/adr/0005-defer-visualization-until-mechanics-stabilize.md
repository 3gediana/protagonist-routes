# ADR-0005 · 先做机制，延后可视化整合

- **状态**：已采纳
- **日期**：2026-05-18
- **背景**：原始 baseline 路线是 `M1 -> M2 -> M3 -> M4 -> M5`。但用户明确表示：**不想看半成品可视化**，宁愿先把核心机制尽量做完整，再一次性做可视化。与此同时，真正的复杂功能（通信 / 合作 / 对抗）依赖的是 `M3/M5` 的能力底座，而不是 `M2` 本身。外部资料也支持在复杂 neuroevolution 迭代期优先用 headless 训练、日志和离线图表驱动调试，而不是过早投入 UI 精修。

---

## 决策

当前项目执行顺序调整为：

```text
M1 收尾验收
→ M3 NEAT 升级（headless-first）
→ M4 多线程 / 异步决策（headless-first）
→ M5 地形核心机制（先完成 physics / perception / world integration）
→ 机制稳定后，再集中做可视化整合
```

### 具体含义

1. **M2 不废弃**
   - `M2` 的设计原则仍然有效：viz 只订阅事件、所有 UI 文案走 i18n、CJK 字体从第一天就正确做。
   - 只是**执行时机后移**，不再作为 `M3` 的硬前置。

2. **M3 / M4 / M5 先按 headless-first 做**
   - 先确保 NEAT、CTRNN、物种分化、异步决策、地形物理等核心机制真实可跑。
   - 调试主要依赖 `CSV / JSONL / plots / observers`，而不是实时 UI。

3. **M5 中所有依赖渲染的验收项顺延**
   - 像等距渲染、视觉截图、FPS 之类，先不阻塞 `M5` 的 core 机制完成。
   - 当前优先完成 TerrainLayer / TerrainPerception / 物理影响 / 资源-地形耦合。

4. **模块顺序不变**
   - 仍然坚持 baseline 完成后再开模块库。
   - 只是 baseline 的实际执行顺序变成“机制优先，展示后补”。

---

## 为什么这样做

### 1. 用户目标是完整展示，不是早期 UI 演示

如果 `M2` 很早接入，只能看到一个还没拓扑进化、没地形、没复杂交互的半成品生态箱。对用户来说这不是加分，而是分散注意力。

### 2. 真正决定后续复杂行为上限的是 M3 / M4 / M5

- `M3` 决定网络拓扑是否可进化、物种是否分化
- `M4` 决定训练吞吐和异步节奏是否成立
- `M5` 决定世界是否具备真实生态位

通信 / 合作 / 对抗这些目标，真正依赖的是这三层，而不是早期可视化。

### 3. 复杂 neuroevolution 更适合先做 headless 验证

外部资料显示：
- NEAT 的关键风险点在**创新号一致性、物种分化、fitness sharing、递归网络稳定性**
- CTRNN 的关键风险点在**状态更新与数值稳定性**

这些问题更适合先通过日志、统计、离线图表和长跑验收来解决，而不是通过 UI 先“看起来能动”。

---

## 代价与补偿

### 代价

- 早期阶段缺少实时画面，用户短期观感不会提升太多
- `M5` 文档中的一部分视觉验收项需要后移

### 补偿

- 统一补一轮可视化时，不会反复推翻 UI
- 更容易把最终展示一次做到位
- 机制和渲染分离会更彻底

---

## 对现有规则的影响

### 与 ADR-0004 的关系

ADR-0004 的原则“前一步完美才加下一步”仍然成立，**但这里把‘当前真正的瓶颈’定义为机制链路，而不是展示层**。

也就是说：
- 当前不允许跳过 `M1` 的机制验收直接做 `M3`
- 但允许在用户明确要求下，把 `M2` 从“执行顺序中的下一步”改成“机制稳定后的整合步骤”

这属于**执行顺序例外**，不是放弃渐进开发。

---

## 结果

从本 ADR 起：

- `PROGRESS.md` 中将明确标注 `M2` 为**延后执行**
- `M3` 的前置条件改为**M1 机制验收到位 + 可视化按本 ADR 延后**
- 后续开发默认按 `M1 -> M3 -> M4 -> M5 -> 可视化整合 -> modules` 推进
