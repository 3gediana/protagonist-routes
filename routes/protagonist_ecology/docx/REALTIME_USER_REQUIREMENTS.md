# REALTIME_USER_REQUIREMENTS.md · 用户实时需求汇总

> 说明：这份文件用于持续汇总用户在当前会话里提出的实时想法与目标效果，供另一个正在开发项目的 AI 直接读取和执行。
>
> 规则：
> - 这里的条目默认都按 **必须实现的硬需求** 处理，不要擅自降级成“可选建议”。
> - 用户原话往往是口语化、压缩的；这里已经做了工程化扩写。
> - 除非用户后续明确推翻或修改，否则旧条目继续有效。
> - 实现时应优先保证“真实机制存在并驱动行为”，不要只做表面数值或装饰性 UI。

## R-001 · 全体个体统一生理状态系统

### 用户原意

用户希望当前 route 中的“血量、口渴、核心体温、饥饿”等状态，像游戏角色那样是真实存在于系统中的个体级数值，而不是只有少量抽象代理指标。用户明确要求：

- 不只是主角，**所有活着的个体** 都必须有这套生理状态。
- 个体应根据自身状态值变化做出行为，而不是恒定模式行动。
- 低于不同阶段阈值时，应触发不同强度的 debuff，而不是只有单一硬阈值。
- 季节必须能真实影响这些核心生理值。
- 长时间运动应显著增加口渴与饥饿消耗；如果当前没有饥饿系统，则必须补上。

### 当前代码现实（供开发 AI 校准，不要误判为已完成）

截至当前代码现实：

- 已存在的 route 级真实状态主要只有 `health` 与 `hydration`。
- 当前 `SurvivalStatusLayer` 只跟踪 protagonist，不是所有活体个体。
- 当前还没有统一的 `hunger` 独立数值。
- 当前还没有统一的 `core temperature` / `body temperature` 独立数值。
- 当前 `season` 层已存在，但尚未与口渴 / 饥饿 / 核心体温衰减建立真实耦合。
- 当前运动主要消耗 `energy`，还没有把运动时长 / 强度显著耦合到口渴、饥饿、体温变化。
- 当前脱水 / 受伤更接近单阈值逻辑，还不是多阶段生理 debuff 系统。

### 必须实现的目标

需要把当前的零散生存机制升级成一套 **全体个体统一生理系统**，至少包含：

- `health`
- `hydration`
- `hunger`
- `core_temperature`

其中：

- **health**：最终生命安全值，不应再承担所有生理逻辑本体。
- **hydration**：真实口渴/含水状态，影响行动能力与健康风险。
- **hunger**：真实饥饿/饱腹状态，必须独立存在，不能仅拿 `energy` 敷衍替代。
- **core_temperature**：核心体温，必须是真实连续数值，不是简单“冷/不冷”布尔量。

### 作用对象范围

这套系统必须作用于：

- protagonist
- 所有 background species
- 后续新增的活体个体

也就是说，**不能再出现“只有主角有真实生理系统，背景物种只是简化 energy 盒子”** 的情况。

### 行为驱动要求

个体行为必须由自身生理状态真实驱动，而不是只由外部奖励或脚本式优先级驱动。至少应满足：

- 口渴上升后，个体更倾向找水、回水源、缩短高消耗活动。
- 饥饿上升后，个体更倾向找食物、改变觅食/捕猎/搬运优先级。
- 核心体温过低时，个体更倾向靠近火源、巢穴、避风处，减少暴露。
- 核心体温过高时，个体更倾向降温、远离高热环境、降低长时间高强度运动。
- 这些行为变化应是连续增强的，不应只有“低于某个点突然像脚本一样切模式”。

### Debuff 机制要求

必须把当前单阈值式生存惩罚升级为 **多阶段阈值 + 连续恶化** 机制。

示例要求：

- `hydration` 低到轻度区间：开始出现轻微负面影响。
- 低到中度区间：移动/判断/恢复效率进一步下降。
- 低到重度区间：显著受损，并开始快速转化为健康风险。
- `hunger`、`core_temperature` 也应有类似多阶段衰减结构。

重点要求：

- debuff 应该是 **分阶段增强** 的。
- 各生理值的严重恶化应可相互叠加。
- 最终 `health` 更像这些长期失衡的综合后果，而不是所有系统直接绕过中间层只改血量。

### 季节与环境耦合要求

季节必须真实改变核心生理系统，而不是只做视觉或上下文标签。

至少要实现：

- **冬季**：核心体温下降更快，保温需求明显增强。
- **夏季**：核心体温上升更快，散热需求明显增强。
- 不同季节下，水分与食物压力也可以不同，但至少体温这一层必须真实耦合。

进一步要求：

- 如果同时存在昼夜、地形、洞穴、营火、巢穴、水域等环境机制，应允许这些因素共同影响个体体温变化。
- 也就是说，`season` 不应独立悬空存在，而应进入真实生理更新方程。

### 运动负荷耦合要求

长时间运动或高强度运动必须带来更高的生理消耗，至少包括：

- 运动越久，`hydration` 下降越多。
- 运动越久，`hunger` 下降越多。
- 高强度或持续运动会改变 `core_temperature`。

用户明确想要的不是“站着和狂奔几乎一样耗状态”，而是更接近真实生命体的负荷变化。

### 感知与决策要求

每个个体必须能够感知自己的这些生理状态，且这些状态应进入其决策回路。

至少需要保证：

- 自身生理状态进入感知/输入，而不是只存在于世界层但脑拿不到。
- 背景物种也不能被排除在外。
- 后续指标和 trace 应能证明这些状态真的参与了行为变化。

### 指标、Trace 与验证要求

实现后必须补足可验证证据，避免“机制写了，但外部看不出来”。至少需要：

- 每个个体级 trace 中可看到 `health / hydration / hunger / core_temperature`。
- 汇总指标中能看到全体活体个体的这些状态统计，而不是只看 protagonist。
- 能区分轻度 / 中度 / 重度生理压力人数或比例。
- 能验证季节切换前后，核心体温变化速率确实不同。
- 能验证高运动负荷个体比低运动负荷个体更快消耗口渴/饥饿，并出现相应行为变化。

### 验收标准

另一个开发 AI 实现这条需求时，至少应达到以下验收结果：

1. 所有活体个体都拥有统一生理状态，而不是 protagonist-only。
2. `hunger` 与 `core_temperature` 作为真实独立数值存在。
3. 生理状态具有多阶段阈值与逐步加重 debuff，而不是单点触发。
4. 冬夏季节会真实改变核心体温演化速度。
5. 持续运动会显著增加口渴与饥饿消耗，并影响体温。
6. 个体会因这些内部状态变化而表现出对应求水、觅食、取暖、避热等行为倾向。
7. trace / metrics 能清楚证明上述机制已经真实接入，而不只是代码里“名义存在”。

### 实现优先级

高优先级。

这是底层生命机制，不是装饰性 feature。若这层不真实，后续很多“像活物一样”的行为都会显得假。

## R-002 · 生产世界必须是可参与、可干预、持续演化的活生态系统

### 用户原意

用户希望所谓“生产世界”不是一个只能旁观的静态展示场，而是一个**用户能够实际进入、实际施加影响、并持续观察系统如何响应与演化**的长期运行世界。用户明确要求：

- 用户应能向系统“投放”事件，直接影响世界。
- 系统里的生物应当对这些刺激作出响应，而且是所有生物，不只是主角。
- 在生产系统中，生物也应能够继续进化自己的网络，而不是上线后完全冻结。
- 最终理想画面是：用户可以像“玩家”一样进入世界，近距离观察这些生物。
- 这些生物需要有较精致的 3D 模型和动作表现。
- 四季更替时环境应真实变化。
- 地形差异化应明显。
- 各种行为之间应存在关联，不能像彼此孤立的功能开关。

### 核心定位要求

生产世界的定位必须明确为：

**一个用户可参与干预的长期生态运行环境**，而不是“训练结束后的只读回放场景”。

这意味着生产世界至少同时承担以下角色：

- **持续存在的生态环境**：世界不是短时 demo，而应支持长期运行。
- **用户参与界面**：用户不是只能看，而是能向世界施加影响。
- **行为观察场**：用户能近距离观察个体、群体、季节、地形、互动的真实变化。
- **持续学习 / 持续演化场**：系统上线后仍具备继续适应和继续变化的能力。

### 用户参与与事件投放要求

必须为生产世界设计一套明确的“用户干预入口”，允许用户像玩家或世界干预者一样向系统投放事件。

这些事件不应只是装饰性特效，而应是真正进入世界机制并改变生态状态的输入。至少应支持以下方向：

- 投放环境事件
- 投放资源变化
- 投放危险或扰动
- 改变局部地形或通行条件
- 改变局部气候 / 温度 / 季节压力
- 向局部区域引入新的机会或威胁

关键要求：

- 这些投放事件必须被世界中的真实机制消费。
- 事件必须能改变个体处境，而不是只在 UI 层显示一下。
- 用户干预后，应能从行为与指标中看到系统响应。

### 全体生物响应要求

用户明确要求：**系统里面的生物（所有）理应对这些刺激做出响应**。

因此必须避免以下错误实现：

- 只有 protagonist 对事件有反应，背景物种无感。
- 只有脚本单位会响应，进化个体不响应。
- 事件只影响数值统计，不影响个体决策。

正确要求应是：

- 所有活体个体都能感知与自己相关的外部刺激。
- 不同物种、不同状态、不同位置的个体可出现不同响应。
- 事件影响应沿着“感知 -> 内部状态 -> 决策 -> 行为 -> 生态后果”完整传递。
- 响应应当允许短期应激和长期适应两层同时存在。

### 生产环境持续进化要求

用户明确希望：在生产系统当中，生物也要能一直进化自己的网络。

因此生产世界不能被定义成“训练结束后参数永远冻结”的纯展示模式。必须支持某种形式的**持续进化 / 持续学习 / 持续更新**机制。

这里的重点不是限定只能采用某一种技术路线，而是必须满足结果要求：

- 生物上线后依然能够继续适应环境与用户干预。
- 网络结构、参数或族群分布应允许继续变化。
- 世界中的长期变化不能永远只靠训练前学到的旧知识硬撑。

但实现时必须同时满足稳定性要求：

- 不能让生产世界因为无门槛在线自我修改而迅速崩坏。
- 需要保留版本管理、回滚、影子评估或分层放行等安全机制空间。
- “持续进化”必须是可观测、可审计、可约束的，而不是黑箱漂移。

### 玩家进入世界的目标体验

最终目标体验必须包含“用户像玩家一样进入这个世界”。

这不是单纯开一个 free camera 就算完成，而是要求形成**玩家尺度的近距离观察体验**。至少应支持：

- 用户进入世界中的一个具体观察视角或角色视角。
- 用户可以近距离看个体如何移动、觅食、避险、协作、受环境影响。
- 用户能够感受到个体不是抽象点，而是具有存在感的生物。
- 用户干预世界后，可以在局部现场直接观察连锁反应。

### 3D 模型与动作表现要求

用户明确要求最终看到的是较精致的 3D 生物，而不是长期停留在简陋占位体。

因此最终展示层必须朝以下方向实现：

- 生物具有相对精致的 3D 模型。
- 不同类型个体在体型、轮廓、动作气质上有区分。
- 动作系统不能只有滑动位移，至少要有基本可信的运动、转向、待机、觅食、攻击/逃避、交互等表现。
- 行为动画应尽量与内部状态或实际行为对应，避免“模型在演，机制在另一套世界里跑”的割裂感。

### 四季与环境视觉变化要求

用户希望四季更替时环境本身也会变化，因此四季不能只体现在后台参数表上。

必须追求两层同时成立：

- **机制层变化**：季节真实影响环境压力、资源条件、生理负担等。
- **视觉层变化**：用户能直接看出季节切换带来的环境差异。

可接受的目标方向包括但不限于：

- 植被/地表色调变化
- 水体、积雪、干燥度、能见度或天气感变化
- 营火、巢穴、遮蔽物等环境设施在不同季节的重要性变化

### 地形差异化要求

用户明确要求地形差异化要明显，因此地形不能只是远看有起伏、近看行为无差别的背景板。

必须让地形同时在以下层面显著存在：

- **视觉存在感**：不同区域一眼能看出明显差异。
- **通行差异**：移动成本、路径选择、可达性不同。
- **生态差异**：资源、藏身、暴露、危险分布受地形影响。
- **行为差异**：个体在不同地形上的决策与生存方式不同。

### 行为关联性要求

用户明确要求“各种行为之间要有关联”。这意味着系统不能做成一堆互不相干的小 feature。

必须让行为之间形成因果链和联动关系，例如：

- 季节变化影响体温与资源，再影响迁移、觅食、取暖与合作。
- 地形变化影响寻路与暴露风险，再影响觅食、逃跑、捕猎与建造。
- 用户投放事件改变局部压力，再影响群体聚散、通信、竞争与恢复。
- 持续进化进一步改变个体如何解释这些压力与机会。

最终要求是：用户近距离观察时，能够感到“这个生态系统里的事情是互相牵动的”，而不是每个模块各演各的。

### 验收标准

另一个开发 AI 实现这条需求时，至少应达到以下结果：

1. 生产世界被明确实现为可长期运行、可用户参与干预的系统，而非只读展示。
2. 用户能够向世界投放会真实改变机制状态的事件。
3. 所有生物都会对这些刺激产生可观察响应，而不是 protagonist-only。
4. 生产世界中存在持续进化 / 持续学习 / 持续更新能力，而不是彻底冻结。
5. 用户能够以玩家尺度近距离观察世界中的个体与群体。
6. 最终展示目标明确包含较精致的 3D 模型与动作，而非长期停留在占位表现。
7. 四季更替能同时体现在机制层与视觉层。
8. 地形差异在视觉、通行、生态、行为上都足够明显。
9. 不同行为机制之间能形成可观察的联动与因果链，而不是功能孤岛。

### 实现优先级

高优先级，但属于**路线级终局定位约束**。

这条需求不一定要求马上把完整 3D 玩家体验一次性做完，但后续所有 live / production / world / interaction / visualization 设计都必须以这个方向为准，不能把生产世界收缩成“只做个观察窗口”或“只做个静态演示厅”。

## R-003 · 机制迭代必须采用“分层验证 + 兼容迁移 + 小任务重训”工作流，不能依赖旧训练模型始终可用

### 用户关注的问题

用户指出了当前项目研发中的一个真实工程难题：

- 后续要补的机制很多。
- 每个机制的完善过程往往不是一次性把输入输出全处理好，而是会经历多轮改动。
- 发现问题时，常常需要单独做一个训练单元或专项场景来验证该机制是否真的可学、可用。
- 但单独训练单元往往又需要一个已经训练好的模型，比较费时间。
- 更麻烦的是，一旦机制改动触到底座，过去训练出来的模型可能根本不适配，甚至完全无法识别新的测试单元。

用户需要的不是一句“重新训练就好”，而是一套**系统性的机制研发方法**，让项目在长期扩机制时不会被“旧模型失效”这件事反复卡住。

### 文献里可借鉴的几条思路

针对这个问题，相关研究并没有一篇论文给出唯一答案，但有几类思路非常适合组合使用：

- **Net2Net / Network Morphism**
  - 核心思想：在扩宽、加深、改结构时，尽量保持原网络函数不变或近似不变。
  - 对本项目的启发：如果只是加容量、加分支、加壳层，不要立刻把旧能力打碎；先让新结构以“兼容模式”接入。

- **Policy Distillation / Teacher-Student**
  - 核心思想：让旧模型当老师，把已有能力迁移到新模型上。
  - 对本项目的启发：当脑结构或输入布局变化较大时，可以让旧模型在参考场景里出行为，新模型先学会模仿旧行为，再继续学新机制。

- **Progressive Networks**
  - 核心思想：旧网络保留，新任务加新列/新分支，通过侧向连接复用旧知识，避免直接覆盖旧能力。
  - 对本项目的启发：对于高风险机制升级，可以保留旧路径，把新机制先做成附加分支或附加控制层，而不是一次性替换整颗脑。

- **EWC / replay / continual learning**
  - 核心思想：在学习新东西时，保护对旧任务重要的参数或经验，减轻灾难性遗忘。
  - 对本项目的启发：未来 live / production 持续学习时，不能无约束在线乱改；需要旧任务回放、基准场景、重要参数保护或影子评估。

- **Incremental Shaping / Curriculum / Scaffolding（进化机器人）**
  - 核心思想：复杂能力不要直接扔进大世界硬训，而是先在脚手架环境中学会局部能力，再逐步增加世界复杂度。
  - 对本项目的启发：新机制应先在 micro-task、小世界、短 episode 中证明“可被学会”，再并入主生态训练。

### 本项目必须采纳的核心结论

对 `routes/protagonist_ecology`，最适合的不是单独选其中一种，而是采用以下组合原则：

- **机制验证不依赖旧大模型**
- **兼容升级时尽量保留旧功能**
- **不兼容升级时明确 version gate，允许 fresh start**
- **所有新机制先过 micro-task / 脚手架验证，再进入大生态训练**

也就是说，项目后续不能继续默认使用“先改机制 -> 再拿旧模型试试看还活不活”这种脆弱流程。

### 机制变更的四类分级

另一个开发 AI 在实现新机制前，必须先给本次改动归类，因为不同类别对应不同验证/迁移方案。

#### A 类：纯接线/观测改动

例如：

- 新 trace 字段
- 新 metrics 字段
- 事件序列化
- 不改变 brain 输入输出维度的内部日志增强

要求：

- 这类改动不应要求重训。
- 只需做 unit test、trace 对照、smoke 验证。

#### B 类：兼容型机制扩展

例如：

- 给 brain 增加新壳层，但旧主路径仍保留
- 增加 body-state slow memory，总输入可通过兼容折叠接入
- 新增世界层，但不打破旧 action 语义

要求：

- 优先采用 Net2Net / Network Morphism 风格的**兼容接入**。
- 初始状态下应尽量不破坏旧行为。
- 允许旧 checkpoint 在“降级使用新机制”模式下继续跑。

#### C 类：部分不兼容升级

例如：

- 输入布局明显变化
- action head 语义调整
- 旧 controller 能力还能参考，但无法直接无损继承

要求：

- 应采用 teacher-student / distillation / replay 参考集迁移。
- 不应直接假设旧 checkpoint 可以裸 resume 成功。

#### D 类：彻底不兼容升级

例如：

- genotype / brain schema 大改
- 核心状态空间重写
- 决策语义整体变化，旧策略已不再有意义

要求：

- 必须明确 `version gate`。
- 必须允许 fresh start。
- 不得为了“保旧模型”而牺牲新机制正确性。

### 本项目的标准验证金字塔

后续所有行为机制都必须按以下 5 层验证，不允许直接跳到正式大训练。

#### L0 · 单元与接线验证

目标：证明机制本体存在且代码路径通了。

适用内容：

- config parser
- event bus 事件
- layer 更新逻辑
- perception/capability 维度
- ledger / memory 写入

项目落点：

- `tests/route_protagonist/`
- `tests/core/`
- route config parser tests

#### L1 · 无训练脚本验证

目标：证明不依赖已训练模型，也能人工触发该机制并观察结果。

可采用：

- 固定动作 agent
- 手写规则 agent
- runtime 注入事件
- 极简 traceprobe 场景

项目要求：

- 每个关键新机制都应至少有一种“无训练可触发”验证。
- 不能把“需要训出来才看得到”当成唯一验证方式。

#### L2 · 专项 micro-task / 小脚手架训练

目标：证明该机制**可被学会**，而不是只在代码里存在。

特征：

- 小地图
- 少变量
- 短 episode
- 少代数
- 明确逼迫该机制被使用

项目落点示例：

- DNC cue-choice task 就属于这一类
- 后续 communication、thermoregulation、causal credit 都应各自有 micro-task

#### L3 · 集成短训

目标：证明新机制进入 route 主训练世界后没有立即把系统打崩，并且开始出现可观测增益。

要求：

- 使用 smoke / short benchmark
- 输出 trace / metrics / ablation 对照
- 明确区分“接线通了”和“能力成熟了”

#### L4 · 正式长训

目标：证明该机制在长期进化中真正改变了生态行为。

要求：

- 仅在前 4 层都过后再进行
- 开正式长训仍保留用户决策权

### 本项目的实际开发流程

另一个开发 AI 以后每做一个行为相关机制，都应按以下步骤执行：

1. **先定义机制目的**
   - 这个机制到底想改变什么行为。
   - 如果机制成功，外部应看见什么新现象。

2. **定义“逼机制发力”的专属任务**
   - 不能把机制扔进大世界再赌它自己会发光。
   - 必须设计一个小任务，让“不用该机制就过不去”。

3. **先做 L0/L1，无训练验证**
   - 先证明机制存在、事件通、指标能记录。

4. **再做 L2，小任务从头短训**
   - 这里允许 fresh small model。
   - 目标不是拿到强模型，而是回答“这个机制能不能被学会”。

5. **通过后再接入主 route smoke**
   - 看是否与现有 memory / goal / ecology 兼容。

6. **最后才考虑是否值得进正式长训**
   - 只有明确带来行为收益的机制，才值得烧长时间训练预算。

### 旧模型失效时的处理规则

必须明确：**旧模型因为机制升级而失效，是正常工程现象，不是失败本身。**

正确处理规则应为：

- 如果是 A/B 类改动：优先保兼容。
- 如果是 C 类改动：做迁移，不强行裸 resume。
- 如果是 D 类改动：明确声明旧 checkpoint 作废，走 fresh train。

绝不能因为舍不得旧模型，就把本来应当做对的新机制压缩成假机制、弱机制或装饰性机制。

### 对 protagonist_ecology 的具体落地建议

结合当前项目，后续建议直接按下面方式执行：

- **通信语义**
  - 先做 `scout-worker` / `danger-warning` / `build-request` micro-task
  - 先验证 signal 是否真的改变 listener policy，再并入主生态

- **统一生理系统（口渴/饥饿/体温）**
  - 先做 thermoregulation / thirst-return 小任务
  - 验证不依赖大世界长训，也能学出找水、取暖、避热

- **因果信用分配**
  - 先做单机制 credit traceprobe
  - 例如只验证 signal -> ally action -> reward attribution 是否成立

- **连续时间机制**
  - 先在单动作持续任务里验证 `move/eat/drink/chop/build` 的持续时间语义
  - 不要等全部世界都改完才一次性总验收

- **World Model / Goal System**
  - 先用固定场景证明 predictor 或 goal persistence 真改变行为稳定性
  - 再并入主 route

### 需要建立的项目级基础设施

为了让上面的流程长期可执行，本项目后续应补足以下基础设施：

- 一组标准 micro-task configs
- 一组标准 traceprobe configs
- 机制级 smoke configs
- 机制级 ablation harness
- schema / checkpoint version 标识
- 参考行为回放集（供 distillation / replay / 回归对照使用）
- 统一的“兼容 / 半兼容 / 不兼容”变更记录规范

### 验收标准

另一个开发 AI 应把这条工作流当成长期研发约束，至少达到以下结果：

1. 后续新增机制不再默认依赖“旧训练大模型”来完成第一轮验证。
2. 每个重要新机制都有自己的 L0/L1/L2 验证路径。
3. 兼容性改动与不兼容性改动会被明确分级，而不是含混处理。
4. 旧 checkpoint 失效时，有清晰的迁移或 fresh start 决策，而不是临时拍脑袋。
5. 项目整体训练预算优先花在“已通过小任务证明有价值”的机制上。
6. 不再为了保住旧模型而牺牲真正需要的新底层机制。

### 实现优先级

高优先级。

这不是单个机制，而是后续所有机制研发的**方法论底座**。如果没有这套工作流，项目会不断陷入“机制刚改一点 -> 旧模型失效 -> 不敢继续改 -> 只剩小修小补”的恶性循环。
